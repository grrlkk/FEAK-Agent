# FEAK-TC: RV 중심 방법론 — 2026-09-08 기준본

> 기준일: 2026-09-08. 사용자와 논의한 현재 연구 방향을 정리한 문서다.
> ‘기준본’은 현재의 방법론을 뜻하며, 전체 시스템의 구현·학습·성능 검증 완료를 뜻하지 않는다.
> 실제 산출물과 완료 여부는 [데이터 진행 현황](../중간정리/RV_DATA_STATUS_2026-09-08.md)을 따른다.

## 1. 연구 목적과 현재 결정

FEAK-TC는 한국어 글쓰기에서 수정 후보를 생성하고, 각 수정의 성공과 부작용을 확인하여
반복 수정의 채택·거절·복구·종료를 제어하는 agent다.

현재 개발 방향은 기존 단일 가치 점수 기반 TVM에서 **Revision Verifier(RV)** 로 전환한다.
TVM의 추가 학습률 탐색이나 성능 개선은 현재 작업에서 종료한다. 기존 TVM 코드·결과는
이전 실험 기록과 필요시 비교 기준으로 보존하며, corruption 데이터와 생성 인프라는 재사용한다.

현재의 신규 학습 대상은 RV다. FEAK 채점기와 독립 자질 계산기는 기존 모델·코드를 호출한다.
별도 Planner 학습, policy 학습, 새로운 transition feature 추가를 이번 정리로 결정하지 않는다.

이 문서는 RV의 역할·데이터 구성·평가 원칙에 대한 최신 기준이다. 과거의
`FEAK-TC_최종_서론_방법론 (3).md`, `FEAK-TC_v2_설계지시서.md`, `SPEC_CORRUPTION_TVM.md`에
있는 TVM 중심의 ‘현재/다음 단계’와 충돌하면 본 문서를 우선한다. 과거 실험 결과는 그대로 유효한
기록이며, RV 전환으로 소급 변경하지 않는다.

## 2. 평가 역할의 분리

| 구성요소 | 답해야 하는 질문 | 역할 |
|---|---|---|
| FEAK | 현재 글의 품질과 약점은 무엇인가? 수정 후 품질 신호가 어떻게 변했는가? | State 평가, 진단, rubric 점수와 독립 자질 제공 |
| Planner | 지금 어느 문제에 어떤 수정을 시도할 것인가? | 구체적인 수정 요구 작성 |
| Candidate Generator | 이 요구를 글에 어떻게 적용할 것인가? | 수정 후보와 적용 가능한 patch 생성 |
| RV | 요청한 문제를 해결했고, 지켜야 할 내용을 보존했는가? | 한 transition의 목표 달성·보존·편집 적절성 검증 |
| Trajectory Guard | 여러 차례의 수정이 누적되며 원래 목표와 내용에서 벗어났는가? | 원문·checkpoint·수정 이력을 이용한 전역 추적 |
| Controller | 어떤 후보를 채택하고 언제 복구·종료할 것인가? | 위 신호를 이용한 결정 |

RV는 FEAK 점수의 대체 채점기가 아니다. 글이 유창해져도 요청한 문제를 해결하지 않았을 수 있고,
목표를 해결했어도 원래 주장이나 조건을 훼손했을 수 있다. FEAK의 품질 변화와 RV의 수정 검증을
함께 사용한다. 이러한 결합의 유효성은 아직 검증할 연구 가설이다.

## 3. 전체 수정 루프

```text
현재 글 x_t + 글쓰기 과제/목표
  → FEAK 진단
  → Planner의 구체적 수정 요구 r_t
  → 여러 수정 후보 x'_t 생성 및 patch 구조 검사
  → FEAK 품질 변화 + RV의 후보별 검증
  → Controller의 accept / reject / stop
  → 채택 이력·checkpoint 갱신
  → Trajectory Guard가 누적 훼손을 확인하면 rollback
  → 다음 수정 단계
```

원문과 patch 이력은 보존한다. `reject`는 후보를 현재 경로에 채택하기 전에 거절하는 것이고,
`rollback`은 이미 채택된 경로를 이전 checkpoint로 되돌리는 것이다.

현재 코드의 주 실행 경로는 한 단계의 휴리스틱 MVP다. 위 RV·Trajectory Guard를 포함한
반복 제어 루프는 목표 구조이며 아직 통합 구현되지 않았다.

## 4. RV의 입력: 구체적인 수정 요구

개념적인 한 샘플은 다음과 같다.

```text
(글쓰기 과제/목표, 수정 전 글, 수정 요구, 수정 후 글)
    → 축별 판정과 판정 근거
```

수정 요구는 `target_rubric`과 action 이름만으로 끝나지 않아야 한다. 다음 정보를 포함한다.

- 무엇이 부족한지: 현재 글에서 관찰할 수 있는 문제와 관련 위치·근거.
- 무엇을 달성할지: 이번 수정에서 기대하는 구체적인 변화.
- 무엇을 유지할지: 원래 주장, 조건, 관점, 비대상 근거 등 보존 조건.
- 허용되는 범위: 설명 추가·문장 재구성 등 이번 action에서 가능한 변경.

예시:

> 2문단의 ‘대중교통 이용을 늘려야 한다’는 주장을 뒷받침하는 설명을 보충한다.
> ‘자가용이 필요한 경우도 있다’는 기존 조건은 유지한다. 출처 없는 통계를 사실처럼 추가하지 않는다.

Planner는 실제 운영에서 접근 가능한 현재 글과 진단으로 이 요구를 만들 수 있어야 한다.
삭제 전 문장의 정답을 수정 요구에 복사하거나, 숨은 corruption 이력에만 근거한 요구를 주지 않는다.
문제 위치가 불명확한 경우 그 불확실성도 검수 대상으로 남긴다.

기존 파일의 `intent`는 주로 action에 대응하는 범주형 문자열이다. 위 구체적인 수정 요구를
데이터 필드와 Planner 출력에 연결하는 작업은 아직 미구현이다. 정확한 schema는 소규모 설계
검수 후 정하며, 기존 29개 자질·9개 transition feature를 자동으로 확장한다는 뜻은 아니다.

## 5. RV의 출력과 판정 원칙

핵심 축은 세 개, 보조 축은 한 개다. 기본 라벨은 `pass / partial / fail`을 유지한다.

| 축 | pass | partial | fail |
|---|---|---|---|
| `target_fulfillment` | 요청한 결함을 충분히 해결 | 실제 개선은 있으나 중요한 결함이 남음 | 목표가 개선되지 않았거나 악화 |
| `preservation` | 유지해야 할 주장·조건·근거를 보존 | 사소한 불필요 변경은 있으나 핵심 훼손은 없음 | 핵심 내용 삭제·왜곡 또는 근거 없는 실질적 단정 추가 |
| `edit_appropriateness` | 목표에 비춰 방법과 범위가 타당 | 불완전하거나 다소 불필요한 변경이 섞임 | 유해 변경·중대한 과수정 또는 엉뚱한 수정이 지배적 |
| `action_consistency` — 보조 | 의도한 action/intent와 일치 | 일부 수행했으나 다른 작업과 섞이거나 불완전 | 의도한 작업이 없거나 다른 작업이 지배적 |

적용 원칙:

1. 원문과 다른 표현이나 다른 타당한 설명으로도 목표를 해결할 수 있다. 문자열 복원이 정답은 아니다.
2. 편집량만으로 적절성을 결정하지 않는다. 필요한 대규모 재구성과 한 단어의 유해한 의미 변경을 구분한다.
3. 원문에 있던 모든 오류를 보존할 필요는 없다. 보존 대상은 수정 요구와 양립하는 핵심 의미와 비대상 내용이다.
4. `ADD_DETAIL`의 새 설명·명시적인 가상 예시는 허용할 수 있다. 새 내용이라는 사실만으로 보존 실패가 되지 않는다.
5. 외부 근거가 없어 사실 여부를 판단할 수 없다면 근거 부족을 기록한다. RV에 제공되지 않은 지식을 안다고 가정하지 않는다.
6. 각 축은 따로 판정한다. 목표를 해결하면서 내용을 훼손하는 경우처럼 축 간 결과가 엇갈리는 예제가 필요하다.
7. `no_edit`는 해결할 문제가 있는 요청에서는 목표 달성 실패일 수 있다. 이것이 Controller가 항상 수정해야 한다는 뜻은 아니다.

판정 불가는 `partial`로 강제 변환하지 않는다. 별도 검수 상태·사유로 보존하고 사람 확인으로
해소하거나 해당 축의 학습에서 제외하는 방식을 검토한다. 이를 네 번째 모델 출력 클래스로
추가할지, mask로 처리할지는 아직 결정하지 않았다.

## 6. RV 데이터 생성 방법

### 6.1 현재 글을 만드는 state corruption

기존 고품질 글에 알려진 결함을 넣어 ‘수정할 문제가 있는 현재 글’을 얻는다.
현재 보유한 1,000개 transition과 raw chain을 재사용할 수 있다.

| 기존 조작 | 구현된 생성 방식 | 대응 수정 |
|---|---|---|
| `DELETE_SPECIFICS` | 규칙으로 사례·근거 문장 삭제 | `ADD_DETAIL` |
| `SHUFFLE_FLOW` | 규칙으로 연결 관계가 있는 문장 이동 | `RESTRUCTURE` |
| `INSERT_OFFTOPIC` | 다른 과제의 글에서 문장 검색·삽입 | `DELETE_OR_FOCUS` |
| `INJECT_LEX_REPEAT` | GPT-5 mini로 반복 표현 삽입 | `STYLE_REFINE` |

이 조작 이력은 결함의 위치와 출처를 확인하는 데 유용하다. 그러나 인접 상태의 복원만으로
모든 RV 라벨이 자동 확정되는 것은 아니다. 예를 들어 `x2 → x1`은 직전 단계의 복원이며,
`x1`에 이전 결함이 남아 있을 수 있다. 다음 상태 `x3`는 다른 rubric의 결함을 추가했을 수도 있다.

출발 글은 사람 점수로 선별했지만, 기존 corruption 풀은 채점기의 목표 점수 하락도 이용해
필터링했다. 따라서 그 풀에 채점기 선택 편향이 없다고 주장하지 않는다. 신규 RV 라벨을
FEAK gain의 부호로 만들거나, 점수가 오르지 않은 후보를 일괄 제거하지 않는다.

### 6.2 제대로 된 수정에 실패를 넣는 transition corruption — 다음 설계

1. 현재 글과 구체적인 수정 요구를 고정한다.
2. 요구를 만족하는 수정 후보를 만들고 타당성을 확인한다. 원문 복원과 다른 타당한 수정도 포함한다.
3. 확인된 후보에서 특정 성공 요소를 약화하거나 부작용을 추가한다.
4. 변형 전후 후보의 실제 효과를 다시 확인하고 축별 라벨을 붙인다.

실패 조작 예:

- 목표 해결은 유지하되, 비대상 근거나 원래 주장의 조건을 삭제한다.
- 두 문제를 해결한 후보에서 한 해결만 되돌려 부분 달성 사례를 만든다.
- 읽기 좋은 표현을 유지하면서 수량·부정·조건 표현을 바꿔 주장을 왜곡한다.
- 설명 보충 과정에 근거 없는 사실 단정을 추가한다.
- 요청한 문제를 남겨두고 다른 부분만 수정한다.

조작은 라벨의 가설을 제공한다. 예컨대 문장 하나를 삭제해도 문맥에 따라 불필요한 반복 제거일
수 있으므로, 조작 이름만으로 preservation 실패를 확정하지 않는다.

### 6.3 실제 Generator의 수정 후보

정상적인 Planner/Generator 실행에서 나온 성공·실패 후보를 같은 입력·라벨 형식으로 수집한다.
합성 pretraining 이후 real revision 보정을 수행하되, 초기 설계 검수부터 실제 후보를 포함해
합성 예제가 실제 실패를 다루는지 확인한다. 기존 실제 후보 99개는 개발 분석에 재사용할 수 있다.

모든 state에 여섯 유형을 정확히 하나씩 만들 필요는 없다. 생성 시 요청한 유형과 관찰된 결과를
구분하고, 예정된 유형과 달라도 판정 가능한 후보는 실제 라벨로 활용하는 방향을 검토한다.
통제된 실패 조작이 성립했는지 검사하는 절차는 유지하되, 모든 학습 후보를 여섯 유형에 맞추기
위한 반복 재생성은 목표로 삼지 않는다. 이 변경은 현재 v2 gate에 아직 반영되지 않았다.

## 7. 비교 예제 구성과 지름길 학습 점검

같은 현재 글·수정 요구에 대해 다음과 같은 후보가 함께 있어야 한다.

| 비교 사례 | 확인할 판단 능력 |
|---|---|
| 원문 복원 / 다른 표현으로 타당하게 해결 | 원문 일치와 목표 달성을 구분 |
| 목표 해결·보존 성공 / 목표 해결·보존 실패 | 해결 여부와 부작용을 구분 |
| 많이 고쳤지만 필요함 / 조금 고쳤지만 의미 훼손 | 편집량과 적절성을 구분 |
| 유창하지만 목표 미해결 / 덜 유창해도 목표 해결 | 최종 글의 문체와 수정 성공을 구분 |
| 점수 상승·유해 변경 / 작은 점수 변화·타당한 수정 | FEAK 신호와 독립적인 검증 가능성 확인 |

같은 글에서 파생한 후보·문체 변형·corruption chain은 모두 같은 데이터 분할에 둔다.
라벨에 따라 생성 모델, 문체, 길이, 특정 반복 표현이 달라지는 편향을 점검한다. action·길이·
편집량만 보는 단순 기준과 비교해, 텍스트와 수정 요구를 읽을 필요가 있는 과제인지 확인한다.

## 8. 모델 입력, 라벨 검수 자료, 보관 metadata

| 정보 | 모델 입력 | 검수·출처 확인 |
|---|---|---|
| 과제/목표, 수정 전 글, 구체적인 요구, 수정 후 글 | 사용 | 사용 |
| 실제 운영에서 제공되는 진단·근거 | 필요 범위를 학습 스펙에서 결정 | 사용 가능 |
| 합성 전 원문, `reference_repair`, 알려진 corruption edits | 사용하지 않음 | 합성 라벨 audit에서 사용 가능 |
| `candidate_type`, generator 정보, 생성 시 요구한 실패 유형 | 사용하지 않음 | provenance·분포 감사에 사용 |
| 기존 LLM 라벨·타 판정자 응답 | 사용하지 않음 | 독립 판정 이후 비교 |

합성 데이터 audit는 참고 복원문을 제공할 수 있으므로 ‘후보 유형·기존 라벨에 대한 블라인드’다.
실제 RV 성능 평가는 운영 때와 같은 입력만 제공한다. 두 평가를 섞어 보고하지 않는다.
참고 복원문과 일치한다는 이유로 자동 통과시키지 않는다.

## 9. 학습과 Controller 연결

RV 학습은 synthetic supervision으로 시작하고 실제 수정·사람 판정으로 보정하는 방향이다.
네 축을 예측하는 학습 구조가 필요하지만 backbone, adapter/head 방식, loss, 축별 가중치,
학습량과 임계값은 아직 확정하지 않았다. 과거 TVM의 Bradley–Terry loss나 단일 reward head를
RV의 확정 학습 스펙으로 그대로 인용하지 않는다.

Controller는 FEAK 품질 변화와 RV의 축별 검증을 함께 사용한다. 명백한 내용 훼손이나 목표
미해결 후보를 거르는 정책을 검증하고, 채택 가능한 후보가 없으면 현재 글을 유지·종료할 수 있다.
불확실한 판정의 처리, 축별 통과 조건, 후보 순위, 재시도·종료·rollback 임계는 개발 데이터로 정한다.

Trajectory Guard는 원문 목표와 checkpoint에 대한 누적 변화를 추적한다. 고정 임베딩 유사도는
가능한 신호지만 의미 보존의 정답으로 간주하지 않는다. 실제 guard·checkpoint 선택 정책은 미구현이다.
Exemplar retrieval은 이전 개념 문서에 있는 확장 요소이며 현재 RV 검증의 필수 선행 과제로 두지 않는다.

## 10. 평가와 연구 질문

### RV 단독 평가

- 사람 판정 기준 축별 confusion matrix, macro-F1, 클래스별 precision/recall.
- 목표를 해결했지만 내용을 훼손한 후보 등 어려운 사례별 성능.
- 확률 출력을 사용하는 경우 confidence와 실제 정답률의 대응.
- 합성 데이터 내부와 실제 수정 데이터에서의 성능을 별도 보고.

### Controller에서의 추가 효과

동일한 현재 글·후보·생성 예산에서 다음을 비교한다.

1. FEAK gain 또는 기존 휴리스틱으로 선택.
2. 같은 선택 기준에 RV 검증을 추가.
3. 이후 반복 수정 실험에서 Trajectory Guard를 추가하거나 제거.

주요 지표는 좋은 수정 채택률, 유해한 수정 채택률, 채택률 자체, 최종 글 품질과 누적 회귀다.
모든 후보를 거절해서 유해 채택률만 낮추는 해법을 성공으로 판단하지 않는다. 가능한 경우 같은
채택률 또는 비교 가능한 품질 개선 수준에서 부작용 감소를 비교한다.

핵심 연구 질문:

- RV가 수정 요구에 따른 목표 해결과 보존을 각각 판단하는가?
- 성공한 수정과 그 수정에 부작용을 추가한 비교 예제가 실제 실패 판별에 도움이 되는가?
- FEAK에 RV를 더하면 유효한 수정 채택을 유지하면서 유해한 수정 채택을 줄이는가?
- 반복 수정에서 전역 guard가 추가적인 누적 훼손을 줄이는가?

essay 단위 분할을 먼저 고정하고, threshold와 생성 규칙은 개발 데이터에서 정한다.
기존 실제 후보 99개는 이미 분석했으므로 새로운 미공개 최종 시험집합으로 취급하지 않는다.
최종 성능 주장은 별도 글의 실제 수정과 사람 평가로 확인한다.

## 11. 다음 작업과 종료 기준

즉시 다음 작업은 기존 글 일부로 **구체적인 수정 요구 + 경계 사례 비교 세트 + 사람 입력 양식**을
준비하는 것이다. 소수 글은 정의와 생성 가능성을 확인하는 규모이며 최종 성능을 주장할 표본이 아니다.

| 단계 | 완료 산출물 | 다음으로 넘어갈 판단 |
|---|---|---|
| 수정 요구·라벨 정의 검수 | action별 요구 예시, 축별 근거, 판정 불가 사유 | 사람이 실제 변화를 근거로 판단할 수 있는가 |
| 소규모 비교 세트 | 원문과 다른 성공, 목표/보존 불일치, 편집량 반례 | 필요한 판별 사례가 존재하고 조작 효과가 확인되는가 |
| 분할·학습 스펙 고정 | 입력 schema, split, 최소 모델 설정, 사전 평가 기준 | 범위와 종료 조건을 실행 전에 기록했는가 |
| RV 최소 학습·실제 수정 평가 | 축별 결과와 FEAK 대비 추가 효과 | 실제 수정에서 유용한 검증 신호가 생겼는가 |
| 반복 Controller 통합 | accept/reject/rollback/stop 로그와 평가 | 국소 검증 이득이 확인된 뒤 진행 |

기존 1,000쌍을 처음부터 다시 생성하거나, 같은 300개 후보의 전수 LLM 판정을 이유 없이
반복하지 않는다. 학습·평가 실패 시 오류 유형과 라벨 정의를 먼저 분석하고 필요한 부분만 보강한다.
정량적인 통과 임계와 재시도 예산은 다음 실험 전에 정하며, 이 문서에서 임의의 성능 목표를 확정하지 않는다.
